============================================================
1. PROJECT OVERVIEW
============================================================

Project name: SAN Construction
Project type: Multi-page, static-first construction company marketing website
Primary goal: Present SAN Construction as a premium, trustworthy construction brand and generate qualified enquiries.
Implementation approach: React frontend with carefully scoped 3D and cinematic animation.
Target implementation tool: Claude Code

The website should feel like a high-end architecture and construction portfolio: cinematic, polished, confident, image-led, easy to navigate, and fast on mobile devices. It must not look like a generic template or allow visual effects to interfere with reading, navigation, accessibility, or conversion.

The first version uses premium placeholder images and provisional copy. The project must make it straightforward to replace placeholders with approved company information later.

Core outcomes:
- Explain the company's construction-related services.
- Showcase projects and construction quality.
- Build trust through process, capabilities, values, and clear contact details.
- Encourage visitors to submit an enquiry or contact the company.
- Provide an immersive visual experience using selective 3D, scroll-linked motion, and cinematic transitions.
- Work reliably on desktop, tablet, and mobile.
- Keep content pages indexable and accessible.

2. ASSUMPTIONS AND ITEMS TO CONFIRM
============================================================

The following are assumptions, not confirmed facts. Claude Code must not invent them as real company facts.

A1. “All construction-related services” is a broad category. Initial service categories may include residential construction, commercial construction, renovation, interior/fit-out work, architectural coordination, project planning, and construction consultation. These must be clearly marked as provisional until SAN Construction confirms its actual services.

A2. The company name is “SAN Construction”. No approved logo, brand guide, address, phone number, email, registration details, project portfolio, testimonials, awards, or years of experience have been provided.

A3. Use temporary brand styling and clearly identifiable placeholder content. Never invent genuine client names, completed projects, certifications, awards, reviews, project values, statistics, or claims.

A4. The site is primarily static and does not require a custom database, login system, CMS, admin dashboard, or backend API for the initial release.

A5. The enquiry form must send email through a third-party form/email service. The provider, destination email, account, API key, and deployment environment have not yet been selected. The form must not pretend to send successfully until the service confirms success.

A6. 3D assets may use a licensed sample model, a placeholder GLB/GLTF model, or a carefully designed 3D scene. No custom building model has been supplied. Use assets with clear licensing and keep a graceful fallback.

A7. The intended visual direction is luxury cinematic: dark charcoal/black, warm white, restrained bronze/gold accents, architectural imagery, generous spacing, strong typography, and controlled motion. Final brand colors can be adjusted later.

A8. The site language is English unless the owner requests additional languages.

A9. Use a modern evergreen-browser baseline. Do not promise support for obsolete browsers.

A10. The initial release should be deployable to a static hosting provider such as Vercel, Netlify, or another compatible host. Final provider is undecided.

A11. Placeholder contact information must never be displayed as if it were genuine. If real contact details are unavailable, use a clearly marked development placeholder and disable misleading contact actions until configured.

A12. Do not add online payments, user accounts, booking systems, project-management dashboards, or other unrequested features.

Before launch, the owner should confirm:
- Actual service list and service descriptions.
- Logo, brand colors, and fonts if available.
- Company location and service area.
- Official phone, WhatsApp, and email details.
- Real projects and approved images.
- Approved company profile and claims.

- Privacy notice and any required consent wording.

3. TECHNOLOGY STACK
============================================================

Required:
- React
- Vite
- JavaScript or TypeScript; prefer TypeScript for maintainability unless the existing repository establishes another convention.
- React Router for multiple-page navigation.
- Tailwind CSS or a consistent CSS architecture. Do not mix styling systems without a reason.
- Three.js with React Three Fiber and Drei for interactive 3D.
- GSAP with ScrollTrigger for complex scroll-controlled sequences where genuinely needed.
- Framer Motion (Motion for React) for component-level transitions and interface motion.
- Lucide React for icons.
- A form validation approach with accessible client-side validation.
- A third-party email/form service selected before production launch.

Dependency rules:
- Use 3D, GSAP, and Framer Motion selectively. Avoid implementing the same animation with multiple libraries.
- Prefer Framer Motion for entrances, hover states, and route transitions.
- Prefer GSAP/ScrollTrigger for complex timeline-based scroll sequences.
- Prefer React Three Fiber for 3D scenes.
- Use plain CSS for simple transitions.
- Verify current package compatibility before installing dependencies.
- Do not install libraries for features that can be implemented cleanly without them.
- Keep all secrets out of source control and client-visible code.

Suggested setup commands (adjust if the repository already exists):
npm create vite@latest san-construction -- --template react-ts
cd san-construction
npm install
npm install react-router-dom framer-motion three @react-three/fiber @react-three/drei gsap lucide-react
npm install -D tailwindcss @tailwindcss/vite

Follow the current official Tailwind/Vite setup for the installed version rather than copying outdated configuration.

7. ENQUIRY FORM AND EMAIL DELIVERY
============================================================

The website needs a real email delivery integration, not just a visual form.

Recommended implementation:
- Prefer a form service or serverless endpoint that safely sends email.
- A client-side email SDK may be used only if its documented public-key model is designed for frontend use, the account is configured securely, and abuse prevention is in place.
- Never expose SMTP credentials, private API keys, or secret tokens in React source, Vite environment variables prefixed with VITE_, or the built bundle.
- If a secret is required, send the form to a server-side endpoint/serverless function or use a reputable form provider that supports secure static-site integration.

Suggested fields:
- Full name (required)
- Email (required, valid format)
- Phone (optional unless owner requires it)
- Service of interest (select; options must match confirmed services)
- Project location (optional)
- Approximate budget (optional; only if owner wants it)
- Message / project description (required)
- Consent checkbox or privacy acknowledgement if required by the selected service and applicable law
- Hidden anti-spam field or provider-supported spam prevention

Validation:
- Validate required fields and formats on the client for usability.
- Treat server/provider validation as authoritative.
- Show inline field errors with text, not color alone.
- Preserve entered values when submission fails.
- Prevent accidental duplicate submissions while a request is in progress.
- Disable the submit button during submission and show progress text.
- Show a clear success message only after confirmed service success.
- Show a useful failure message and a retry path if sending fails.
- Never expose raw server errors, credentials, or stack traces.
- Add provider-supported CAPTCHA/rate limits/honeypot controls where appropriate.
- Avoid collecting unnecessary personal data.
- Define retention and privacy wording before launch.

Required states:
- Idle
- Client-side validation error
- Submitting
- Success
- Provider/network failure
- Spam/blocked submission if applicable

Configuration:
- Keep public configuration in documented environment variables.
- Keep private secrets in hosting provider secret settings.
- Provide `.env.example` with placeholder names only, never actual secrets.
- Add setup instructions for the selected provider.
- Until provider credentials and destination email are configured, clearly label the form as not production-ready. Do not simulate successful email delivery.

Testing:
- Valid submission.
- Missing required values.
- Invalid email.
- Network/provider error.
- Repeated-click handling.
- Mobile keyboard and field behavior.
- Keyboard-only operation.
- Confirmation that the email reaches the intended inbox and does not expose secrets.

8. 3D EXPERIENCE REQUIREMENTS
============================================================

The 3D experience should be premium and intentional, not a technical demo.

Preferred approach:
- Use React Three Fiber and Drei for a hero scene or selected architectural feature.
- Use a GLB/GLTF model with known licensing, or create a lightweight procedural architectural composition.
- Consider camera movement, subtle model rotation, lighting, material detail, and restrained parallax.
- Connect scrolling to a small number of deliberate scene changes when it adds narrative value.
- Use GSAP ScrollTrigger for complex, pinned scroll sequences only when the experience remains usable on small screens.
- Never make the user scroll through a long animation before reaching useful content.
- Do not force scroll hijacking or lock normal browser scrolling.

Performance and fallback:
- Lazy-load the 3D scene when practical.
- Do not block the initial headline, navigation, or CTA on model loading.
- Provide a static image or CSS fallback if WebGL is unavailable, the model fails, or reduced-motion preferences are active.
- Optimize geometry, texture sizes, draw calls, and model file size.
- Avoid huge uncompressed textures.
- Limit simultaneous lights, shadows, post-processing, and particle effects.
- Pause or reduce animation when the scene is off-screen or the page is hidden, where feasible.
- Avoid mobile overheating, excessive battery use, and continuous unnecessary rendering.
- Respect prefers-reduced-motion.
- Make all important information available in regular HTML, not only inside the 3D canvas.
- Ensure 3D content does not block links, buttons, or keyboard focus.
- Use a loading indicator only if loading is noticeable, and avoid a fake progress percentage.
- Test on integrated graphics and mid-range mobile devices.

9. MOTION AND INTERACTION DESIGN
============================================================

Animation principles:
- Motion must support hierarchy, storytelling, and feedback.
- Use consistent easing and timing.
- Keep interactions responsive and predictable.
- Avoid animating every element.
- Avoid excessive bouncing, flashing, spinning, or competing effects.

Suggested motion system:
- Short hover/focus transitions for buttons and links.
- Gentle opacity/vertical reveal for section content.
- Staggered card reveals with restrained offsets.
- Image reveal or clip-path transitions used selectively.
- Header background transition on scroll.
- Page transitions that do not delay navigation.
- Scroll-triggered process timeline.
- Hero 3D camera/model movement.
- Small interactive feedback for form states.

Motion implementation:
- Use Framer Motion for local component transitions and route-level effects.
- Use GSAP/ScrollTrigger only for complex timeline and scroll choreography.
- Clean up ScrollTrigger instances, event listeners, observers, animation timelines, and RAF loops when components unmount.
- Do not use React state updates on every animation frame when a ref or animation library can handle the visual update.
- Avoid hydration-specific patterns unless the project later adds SSR.
- Keep animation behavior consistent when users navigate directly to a nested route.
- Ensure all interactive elements have visible focus states and usable hover/focus behavior.

Reduced motion:
- Respect `prefers-reduced-motion: reduce`.
- Remove or simplify scroll-linked motion, parallax, automatic camera movement, and nonessential transitions.
- Never rely on animation to communicate essential information.

12. PERFORMANCE AND ASSET OPTIMIZATION
============================================================

Performance goals (targets, not guarantees):
- Aim for Core Web Vitals “good” thresholds on real-user data where measurable:
  LCP <= 2.5 seconds
  INP <= 200 milliseconds
  CLS <= 0.1
- Keep the initial JavaScript bundle as small as practical.
- Lazy-load below-the-fold images and heavy route modules.
- Prioritize the hero image or initial visual, but do not eagerly download every project image.
- Use AVIF/WebP when supported with appropriate fallbacks.
- Specify image dimensions or aspect ratios to prevent layout shifts.
- Compress and resize images to their display dimensions.
- Lazy-load 3D libraries and models.
- Avoid excessive third-party scripts.
- Avoid autoplay video with audio.
- If using video, use a poster image, muted playback, sensible size, and reduced-motion fallback.
- Use route-level code splitting where appropriate.
- Remove unused dependencies and assets.
- Check bundle size and production build output.
- Use caching-friendly filenames and hosting defaults.
- Avoid rendering an expensive 3D scene on every route if not needed.

Measure with:
- Browser DevTools Performance and Network panels.
- Lighthouse or equivalent audit.
- Production build, not only the development server.
- Tests on a mid-range mobile device or throttled profile.
